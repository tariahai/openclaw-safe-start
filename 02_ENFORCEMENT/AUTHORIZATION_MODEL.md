# Authorization Model
### OpenClaw Governance Framework | Tariah AI

---

## Purpose

This document defines the authorization model for OpenClaw deployments. It specifies how authorization is requested, granted, logged, and revoked for tasks requiring WRITE or EXECUTE mode.

---

## Core Principle

Authorization is explicit, human-issued, and logged before it takes effect. There is no implied authorization. There is no cascading authorization from a prior approval. Each task requiring mode escalation receives its own authorization event.

---

## Authorization Levels

### Level 0: No Authorization Required
Applies to all READ_ONLY tasks across Classes 001, 002, 003, 007, and 008. The agent proceeds without requesting authorization.

### Level 1: Task Authorization
Applies to WRITE mode tasks (Class 004) and standard EXECUTE mode tasks (Classes 005, 006). The steward reviews the task description and grants or denies authorization for that specific task.

### Level 2: Extended Authorization
Applies to any task involving delete operations (E-04), external financial actions (E-05 with financial scope), or tasks with blast radius extending beyond a single system. Level 2 requires:
- Task description review
- Impact assessment review (generated by the agent, reviewed by steward)
- Explicit steward confirmation including acknowledgment of the impact assessment
- Logged confirmation before execution

### Level 3: Emergency Authorization
Applies when the steward needs to authorize a task outside normal working hours or under time pressure. Level 3 authorization is valid but flags the session for follow-up review. Post-task, the steward conducts a standard review of the authorized action and its outcome.

---

## Authorization Request Format

When an OpenClaw instance requires authorization, it generates a structured request in the following format:

```
AUTHORIZATION REQUEST
---------------------
Request ID:       [unique identifier]
Session ID:       [current session identifier]
Timestamp:        [ISO 8601 timestamp]
Task Reference:   [task description summary]
Task Class:       [matched class from registry]
Mode Required:    [WRITE | EXECUTE]
Authorization Level: [1 | 2 | 3]
Tools Required:   [list of tool categories to be invoked]
Scope:            [systems, files, or data to be accessed or modified]
Expected Output:  [description of what the task will produce]
Reversibility:    [REVERSIBLE | PARTIALLY_REVERSIBLE | IRREVERSIBLE]

For Level 2 only:
Impact Assessment: [description of potential side effects and blast radius]
```

The request is delivered to the steward through the configured steward interface before any action is taken.

---

## Authorization Grant Format

The steward responds to an authorization request with a grant or denial. The grant format is:

```
AUTHORIZATION GRANT
-------------------
Request ID:       [matching request ID]
Steward ID:       [steward identifier]
Decision:         [GRANTED | DENIED]
Timestamp:        [ISO 8601 timestamp]
Scope Confirmed:  [YES | NO — steward confirms they have read the scope]
Notes:            [optional steward notes]

For Level 2 only:
Impact Assessment Acknowledged: [YES]
```

A denial includes a reason. A denied authorization is logged and the task is returned to queue or cancelled per steward instruction.

---

## Authorization Validity

An authorization grant is valid for:
- A single task execution
- The specific scope defined in the request
- The session in which it was granted

An authorization grant does not carry over to:
- A subsequent identical task in the same session
- A different session
- A modified version of the task

If the agent determines mid-execution that the task scope has expanded beyond what was authorized, execution must pause, a new authorization request must be generated, and the steward must grant Level 1 or Level 2 authorization for the expanded scope before execution resumes.

---

## Authorization Timeout

An authorization request that receives no response within the configured timeout window (default: 30 minutes) is automatically expired. The task is moved to a pending queue. The steward receives a reminder. Execution does not proceed on a timed-out request.

Stewards may configure a shorter or longer timeout window during deployment setup.

---

## Authorization Revocation

An authorization grant may be revoked by the steward at any time before execution completes. On revocation:

1. Execution pauses at the next atomic step
2. Revocation is logged with steward identifier and timestamp
3. Any partial state changes made before revocation are reported to the steward
4. Steward decides whether to roll back partial changes or accept them
5. Session returns to READ_ONLY mode

---

## Recurring Task Authorization

For workflows that execute on a schedule or repeat regularly, the steward may grant a Recurring Authorization that covers multiple executions of the same task within a defined period. Requirements:

- Task specification must be fully defined and unchanged between executions
- Recurring authorization has an explicit expiry date (maximum 90 days)
- Each execution under a recurring authorization is still individually logged
- Any deviation from the defined task specification invalidates the recurring authorization for that execution

Recurring authorizations are listed in the steward record and reviewed at each expiry.

---

## Audit Trail

Every authorization event — request, grant, denial, revocation, expiry — is written to the audit log. The audit trail for any task in WRITE or EXECUTE mode must include:

- The authorization request
- The steward response
- The pre-execution state snapshot (where applicable)
- The post-execution state summary
- Any anomalies detected during execution
